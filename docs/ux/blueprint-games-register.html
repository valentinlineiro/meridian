Meridian's LinkedIn Games register: day-save blueprint

System overview

The register is the only way results enter the Games section of Meridian. The owner types the day's times into a sheet on Hoy or on Games, and a Worker stores them as an append-only version of that day in the snapshots table. Every reading on the Games page, the Hoy row, Qué cambió and the CSV export is computed from the latest version of each day.

This blueprint covers the save path after the redesign: one structured call that adds, changes and removes games for a day, errors that name the game and field, and what the save does when the connection or the session fails. The read path is unchanged apart from Hoy deriving its button label from the summary's to, which is the last day with a played game; the button reads "Editar lo de hoy" when to equals today's date.

One person owns and operates all of it. Risk areas: the append-only table is the single store for every day, and the access policy fails closed, so a write path missing from its list is unreachable from the browser.

Process architecture

Save, step by step. The sheet sends PUT /api/me/linkedin-games/day with date, tz, today, set (game to time and optional average, where avg: null clears a stored average and an absent avg keeps it) and remove (list of games). The server then:

  1. Checks the owner session and the same-origin header.
  2. Validates every row. Any invalid row, a game listed in both set and remove, or a future date, returns 422 with errors[] as { game, field, reason } (field is game, score, avg or date) and writes nothing.
  3. Reads the latest version of the day (or an empty day).
  4. Applies set as today's merge, clears or removes as listed. A removed game's key is deleted from games, which readers already treat as "not collected".
  5. Appends one version with a fresh capturedAt only if the games differ from the latest version.
  6. Returns { ok: true, day, changes: [{ game, status }] } with status new, changed, removed or same.

Decision points. Valid or not (all or nothing); changed or same (append or not). Handoffs. Sheet to Worker carries the diff, not the full day; Worker to the ingest pipeline carries the whole day, as contract L8 requires. Timing. The browser abandons any request after 10 seconds (REQUEST_TIMEOUT_MS); the server has no deadline of its own, so a request may finish after the browser gave up. Exceptions. Each is a row under State and failure analysis.

Operational feasibility. A save is one read of the latest version and at most one append, the same write cost as the per-game save and the text import today, and it never writes for an unchanged day. The refresh after a save is two reads (day, summary). One owner logging once a day is far below any D1 free-plan limit.

Contract changes

Contract L8 (each capture is the day's cumulative; a partial capture would make a reader see fewer games) and L10 (no way to delete a field) conflict with removal and with clearing an average. A new rule L14 states that the owner's day save may delete a game's key and clear an average, that it does so only through PUT /api/me/linkedin-games/day, and that every other writer keeps L8 and L10. The access policy comment and its list gain the new path.
